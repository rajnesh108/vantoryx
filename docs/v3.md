# V3 — Agentic Retrieval

V3 puts a LangGraph agent in front of the V2 hybrid search. The agent plans the search, chooses which document collections to read, and retries when the passages do not cover the question.

| Component | Purpose | Example |
|---|---|---|
| Query planning | Turns one question into one or more search queries | Split “treatment and prevention” into two searches |
| Routing | Chooses document categories | A question that names WHO searches `who` |
| Hybrid retrieval | The V2 search: BM25, vectors, fusion, and the reranker | Same index, no re-upload |
| Grading | Decides whether the passages can answer the question | Missing prevention eligibility fails the grade |
| Rewrite and retry | Searches again with a sharper query | One retry by default |
| LLM | Writes the cited answer from the final passages | The same local or OpenAI-compatible chat model |

```text
User question
    ↓
Plan                         Route
Search queries               Document categories
    ↓
Retrieve — V2 hybrid search
BM25 + vector + RRF + reranker
    ↓
Grade
Do these passages cover the question?
    ↓
Yes → passages go to the answer model
No, and a retry remains
    ↓
Rewrite the query
    ↓
Retrieve again, then grade again
```

`POST /api/chat` runs this graph when `AGENT_ENABLED` is true. The response still has `answer`, `citations`, and `model`. It also has `agent`, a short trace of the plan, route, retrievals, grade, and any rewrite. The search page lists that trace under the answer.

Set `AGENT_ENABLED=false` to keep the V2 path: one hybrid search, no plan, no grade, and `agent` is null.

PostgreSQL, pgvector, and the embedding server stay as they are in [v2.md](./v2.md). Restart the backend after pulling this version. The PDFs do not need to be uploaded again.

## Query planning

The plan node asks the chat model for JSON:

```json
{"queries":["tb preventive treatment","tb treatment"],"reason":"The question asks about two topics."}
```

A single-fact question stays one query. A question with independent parts, such as two organizations or two conditions, can become up to `AGENT_MAX_QUERIES` queries (default 3). The model is told not to answer the question and not to invent clinical facts.

Each planned query is searched with the V2 retriever, so that query is fused and reranked on its own. Those lists are merged with reciprocal rank fusion, and the reranker scores the merged passages against the original question. If the reranker is off, the merged list is cut to `TOP_K`.

If planning fails, or the JSON cannot be read, the graph searches the original question and records that in the trace.

## Routing

Collections are the document categories already stored on each PDF:

| Category | Publisher |
|---|---|
| `who` | World Health Organization |
| `mohfw` | Ministry of Health and Family Welfare |
| `aiims` | AIIMS |
| `icmr` | Indian Council of Medical Research |
| `cdc` | CDC |
| `nice` | NICE |
| `other` | Other publishers |

The route node may keep only the categories the question names. If the question does not name a publisher, every allowed category is searched. A category list sent with the chat request is the ceiling: routing can narrow that list, and it cannot add a category the request left out.

If routing fails, the search uses every allowed category.

## Grading and retries

After retrieval, the grade node reads the passages and returns:

```json
{"sufficient":false,"reason":"The passages cover treatment, not prevention."}
```

`sufficient` is true only when the passages state the facts the question asks for. Empty results are not sufficient. The grader is told not to use outside knowledge.

When the grade fails and `attempts` is still within `AGENT_MAX_RETRIES`, the rewrite node produces one new search query. That query is retrieved and placed ahead of passages already kept. The combined pool is reranked against the original question, or cut to `TOP_K` when the reranker is off. The grade runs again.

The loop stops when any of these is true:

- The grade says the passages are sufficient.
- The retry budget is spent. The default budget is 1, so the graph searches at most twice.
- The rewritten query repeats an earlier search.
- Planning, routing, grading, or rewriting cannot get a usable model response. Retrieval that already succeeded is kept. A failed planner falls back to the original question. A failed router searches every allowed category.

`AGENT_MAX_RETRIES=0` plans and routes once, then does not rewrite.

## Configuration

| Setting | Default | Role |
|---|---|---|
| `AGENT_ENABLED` | `true` | Run the LangGraph retrieval agent |
| `AGENT_MAX_QUERIES` | `3` | Maximum planned queries for one question. Allowed range 1–3 |
| `AGENT_MAX_RETRIES` | `1` | Extra searches after the first grade fails. Allowed range 0–3 |

The V2 knobs still apply inside each search: `BM25_TOP_K`, `VECTOR_TOP_K`, `RERANK_TOP_K`, `RERANKER_ENABLED`, and `TOP_K`.

In code the graph is `compileRetrievalGraph` in `backend-server/src/services/agent/graph.ts`. `POST /api/chat` calls `runAgenticRetrieval` when the agent is on.

## Limits

V3 chooses how to search. It does not add new sources.

- Answers still come only from indexed PDF passages.
- The agent does not browse the web or call external tools. That is V4.
- A retry cannot recover a fact that was never indexed.
- Grading uses the same chat model as the answer, with temperature 0. A weak local model can plan a poor query or stop too early.
