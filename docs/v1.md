# Vantoryx V1 — Basic RAG

V1 is the first version of Vantoryx. It answers questions from uploaded PDFs by retrieving nearby passages and asking a local language model to answer from those passages only.

What V1 demonstrates:

| Piece | What it does |
|---|---|
| Embeddings | Turn text into 768-number vectors with `sentence-transformers/all-mpnet-base-v2` |
| Chunking | Split each PDF into overlapping passages of about 1000 characters |
| pgvector | Store those vectors in PostgreSQL and rank them by cosine distance |

How to start the services is in [configuration.md](./configuration.md).

## What V1 includes

An admin uploads a PDF. The backend extracts page text, splits it into chunks, embeds each chunk, and stores the vectors in PostgreSQL. A reviewer then asks a question. The same embedding model encodes the question, pgvector returns the closest ready chunks, and the language model writes an answer that cites those chunks.

| Area | V1 behavior |
|---|---|
| Documents | PDF only, up to 40 MB, one file per upload |
| Categories | `who`, `mohfw`, `aiims`, `icmr`, `cdc`, `nice`, `other` |
| Search | Cosine similarity over chunk embeddings, default top 5 |
| Answers | Grounded in retrieved passages, with source numbers such as `[1]` |
| Access | Upload and delete require an admin session; search is open |

Later versions add hybrid search, reranking, agents, evaluation, and production serving. Those are listed in the repository `README.md`.

## Document ingestion

Healthcare PDFs are uploaded through the admin section, then indexed before anyone can search them.

```text
Document ingestion — upload healthcare PDFs through the admin section
    ↓
Text extraction
    ↓
Chunking
    ↓
Local embeddings
    ↓
Save in PostgreSQL + pgvector
```

## Search

A question is embedded with the same local model, compared with stored chunks, and answered from those passages.

```text
Enter text query
    ↓
Text extraction
    ↓
Chunking
    ↓
Local embeddings
    ↓
Similarity search
    ↓
Context
    ↓
Call local LLM model
    ↓
Answer + citations
```

Text extraction and chunking belong to ingestion. At search time the question is embedded as one string, then compared with the chunks already stored in pgvector.

The retrieval and generation steps in that path use two separate controls: Top-K chooses how many chunks come back, and temperature chooses how much the language model varies its wording. Both are covered under [Technical concepts](#technical-concepts).

Services involved:

| Service | Role in V1 |
|---|---|
| Frontend (`:5173`) | Upload documents and ask questions |
| Backend (`:4000`) | Ingestion, retrieval, and chat API |
| Embedding server (`:8000`) | PDF text extraction and embeddings |
| PostgreSQL + pgvector (`:5432`) | Documents, chunks, and vector search |
| Ollama (`:11434`) | Local chat model, default `llama3.1` |

## Ingestion

`POST /api/documents` accepts a PDF and a category. The file is saved under `uploads/`, a `documents` row is created with status `processing`, and the response is `202`. Ingestion then runs in the background.

1. The embedding server reads the PDF and returns one text block per page.
2. The backend chunks those pages.
3. Chunks are embedded in batches of 32.
4. Existing chunks for that document are replaced, and the new rows are inserted in one transaction.
5. The document status becomes `ready`, with `page_count` set.

If extraction finds no text, or embedding or the database fails, status becomes `failed` and the error is stored on the document. Scanned image PDFs fail here because V1 does not run OCR.

Deleting a document removes its file and its chunk rows. Chunks use `ON DELETE CASCADE` from `documents`.

## Chunking

Defaults come from `CHUNK_SIZE` and `CHUNK_OVERLAP`.

| Setting | Default | Allowed range |
|---|---|---|
| `CHUNK_SIZE` | `1000` characters | 200–4000 |
| `CHUNK_OVERLAP` | `180` characters | 0–1000, and smaller than `CHUNK_SIZE` |
| Minimum piece kept alone | `200` characters | Shorter pieces merge into the previous chunk when they still fit |

The splitter prefers paragraph breaks, then line breaks, then sentence breaks, then spaces. Each stored chunk keeps `page_start` and `page_end` so citations can name the source pages. Overlap copies the tail of the previous chunk onto the next one so a sentence that crosses a boundary is still searchable.

## Embeddings

The embedding server loads `EMBEDDING_MODEL`, default `sentence-transformers/all-mpnet-base-v2`. That model produces 768-dimensional vectors. `EMBEDDING_DIM` must stay `768`, and the model’s actual dimension must match it.

The backend calls:

| Endpoint | Input | Output |
|---|---|---|
| `POST /extract` | Absolute path of the uploaded PDF | `{ pages: [{ page, text }] }` |
| `POST /embed` | `{ texts: string[] }` | `{ embeddings, model, dimension }` |

Both the stored chunks and the user question are embedded with this same model. A vector from a different model or dimension cannot be compared with the stored rows.

## Storage

`schema.sql` enables the `vector` extension and creates the tables V1 uses.

`documents` holds the file name, storage path, category, status (`processing`, `ready`, or `failed`), page count, and any ingestion error.

`chunks` holds the passage text, chunk index, page range, and `embedding vector(768)`.

Search uses an HNSW index:

```sql
CREATE INDEX IF NOT EXISTS chunks_embedding_hnsw
  ON chunks USING hnsw (embedding vector_cosine_ops);
```

The backend sends embeddings as a pgvector literal, for example `[0.01234567,...]`, and casts it with `::vector`.

If an older database still has 384-dimensional embeddings, startup truncates `chunks`, marks existing documents `failed`, and alters the column to `vector(768)`. Those PDFs need to be uploaded again.

## Retrieval and answers

`POST /api/chat` takes a question of 1–2000 characters, and optional `documentIds` and `categories`.

1. The question is embedded.
2. Ready documents are searched with `ORDER BY embedding <=> query` and `LIMIT TOP_K`.
3. The score returned to the client is cosine similarity: `1 - (embedding <=> query)`.
4. The closest chunks are numbered and sent to the chat model with a system prompt that requires citations and forbids answers that are not in the sources.

If nothing matches, the API returns that message and an empty citation list. If the language model cannot be reached, the API still returns the retrieved passages so the closest text is visible.

The chat client is any OpenAI-compatible `/v1/chat/completions` endpoint. The default is Ollama at `http://127.0.0.1:11434/v1` with model `llama3.1`. Each request sends `temperature: 0.1`.

## Technical concepts

### Top-K

Top-K limits the number of retrieved chunks. It does not guarantee that those chunks are relevant.

In Basic RAG (V1) the value is read here:

```ts
topK: intEnv("TOP_K", 5, 1, 20)
```

| Argument | Meaning |
|---|---|
| `"TOP_K"` | Environment variable name |
| `5` | Default value if the variable is not set |
| `1` | Minimum allowed value |
| `20` | Maximum allowed value |

In `.env`:

```text
TOP_K=5
```

With `TOP_K=5`, vector search returns at most five chunks, those chunks become the prompt context, and the language model answers from them.

RAG with reranking (V2) retrieves a wider candidate set, such as 20 chunks, then reranks and keeps the best 3–5. Top-K still only limits how many chunks are retrieved. It does not guarantee relevance. Add a similarity threshold and evaluate retrieval quality before using a larger candidate set in production.

### Temperature

Temperature controls how predictable or varied the generated response is. It changes the randomness of token selection while the model writes text.

A low temperature keeps answers relatively consistent from the same context. V1 sends `temperature: 0.1` on the chat completion. A setting around `0.2` is in the same low range and produces a relatively consistent answer.

### Top-K and temperature

| Parameter | Controls | Pipeline stage |
|---|---|---|
| `topK: 5` | Number of document chunks retrieved | Retrieval |
| `temperature: 0.2` | Variation in generated output | Generation |

```text
User query
    ↓
Vector search — Top-K = 5
    ↓
Retrieve relevant chunks
    ↓
Build prompt with retrieved context
    ↓
LLM — temperature = 0.2
    ↓
Generate a relatively consistent answer
```

The running chat request uses `temperature: 0.1`, which is the same kind of low-temperature setting as `0.2`. Vectors are saved during ingestion, before this query path runs.

## Configuration

Values live in the repository `.env`. The backend reads them at startup.

| Variable | V1 default | Meaning |
|---|---|---|
| `DATABASE_URL` | local PostgreSQL `vantoryx` | Database with pgvector |
| `EMBEDDING_SERVICE_URL` | `http://127.0.0.1:8000` | Extract and embed service |
| `EMBEDDING_DIM` | `768` | Must match the model and the `vector(768)` column |
| `EMBEDDING_MODEL` | `sentence-transformers/all-mpnet-base-v2` | Model loaded by the embedding server |
| `CHUNK_SIZE` | `1000` | Target chunk length in characters |
| `CHUNK_OVERLAP` | `180` | Characters repeated from the previous chunk |
| `TOP_K` | `5` | Passages sent to the language model |
| `LLM_BASE_URL` | `http://127.0.0.1:11434/v1` | OpenAI-compatible chat API |
| `LLM_MODEL` | `llama3.1` | Chat model name |

Changing `EMBEDDING_MODEL` to a model with a different dimension requires a matching schema change. Changing chunk size does not rewrite existing chunks; upload the PDF again to re-index it.

## Limits

V1 is dense vector search over extracted PDF text.

- Image-only PDFs are not indexed.
- There is no keyword index, hybrid score, or reranker.
- The model does not browse the web or call tools.
- Answers are only as complete as the top retrieved chunks.
