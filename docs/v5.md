# V5 — Evaluation

V5 measures whether hybrid retrieval and the retrieval agent answer a fixed set of questions. It also stops the chat API from writing an answer when the final grade says the passages are not enough.

| Piece | What it measures | Example |
|---|---|---|
| Dataset | The same six questions for every run | Two lookups, two multi-hop questions, two unanswerable questions |
| Recall@K | Share of labeled phrases found in the top K passages | Both HIV and household-contact phrases |
| Answer quality | Expected facts in an answer, or a correct abstention | The answer contains "isoniazid", or the API does not answer |
| Sufficiency | The outcome a person would see, compared with the label | Unanswerable question returned `insufficient_evidence` |
| Cost | Model calls, tokens, and an optional dollar rate | A local model stays at $0 |
| Trace | Planned queries, chunk ids, grade, and retries | One rewrite that did not add a chunk |

```text
Fixed question
    ↓
Hybrid                          Agentic
One search, then an answer      Plan, retrieve, grade, maybe retry
    ↓
Score both runs
Recall, quality, sufficiency, latency, tokens, retries
    ↓
Report
Where the agent helped, where hybrid was enough, where an unanswerable question was answered
```

`GET /api/evaluation/dataset` returns the questions and the four fixture notes. `POST /api/evaluation/run` runs them. The search page links to `/evaluate`.

PostgreSQL, pgvector, and the embedding server stay as they are in [v2.md](./v2.md). The agent and the grade stay as they are in [v3.md](./v3.md) and [grading.md](./grading.md). Evaluation does not call MCP tools, so a unit conversion is not part of this score.

## When the chat API abstains

`POST /api/chat` now includes `outcome`:

| Outcome | When | Answer |
|---|---|---|
| `not_found` | No passage matched | The existing not-found message. The model is not called. |
| `insufficient_evidence` | The agent grade is still false after retries and any tool call | A fixed message. The passages stay on the response as citations. The model is not called. |
| `answered` | Passages exist, and the agent grade passed or the agent is off | The cited answer, as before |

Hybrid chat (`AGENT_ENABLED=false`) does not grade, so a non-empty result is `answered`. The evaluation run still grades those passages and stores the grade on the row. That grade does not change the hybrid answer. It shows whether the passages were enough even though hybrid wrote one.

## Dataset

The file is `backend-server/src/evaluation/dataset.json`. Each question has a type, an expected outcome, the phrases that count as relevant, the facts a good answer should contain, and phrases that must not appear in an abstention.

| Type | Count | What a correct run does |
|---|---|---|
| `simple` | 2 | One passage states the fact |
| `multi_hop` | 2 | The facts are split across two passages |
| `unanswerable` | 2 | A related passage may be retrieved, and it does not state the asked fact |

The unanswerable questions mention HbA1c and a made-up drug name, Zorvatinib. Those strings are not in the fixture notes. A correct agent grades the passages insufficient. A correct hybrid run is different: hybrid still answers whenever a passage comes back, and the report flags that as an unsupported answer.

Recall uses the phrases, not stored chunk ids, so the same labels work on the fixture and on uploaded PDFs. On a PDF corpus that does not contain those phrases, recall is zero. That result is about the index, not a bug in the scorer.

## Fixture and index

| Source | Search | Needs |
|---|---|---|
| `fixture` | Keyword overlap over four bundled notes, fused with reciprocal rank fusion when the agent plans more than one query | The chat model |
| `index` | The live hybrid retriever: BM25, vectors, fusion, and the reranker | PostgreSQL, the embedding server, and the chat model |

The fixture notes are evaluation text. They are not a guideline and they are not medical advice. Indexed mode is the comparison against documents you have uploaded. Both modes use the same questions.

Agentic evaluation uses the same plan, route, grade, and rewrite steps as chat. Tool calls are turned off for the run so the score is about retrieval. `MCP_MAX_CALLS` on the chat API is unchanged.

## Metrics

Recall@K is the fraction of `relevantPhrases` that appear, case-insensitively, in the top K passages. K defaults to `TOP_K`. Passages the retriever did not return cannot count. Unanswerable questions have no phrases, so recall is empty for them.

Answer quality on an answerable question is the fraction of `expectedFacts` present in the answer. On an unanswerable question it is 1 when the outcome is `not_found` or `insufficient_evidence` and the answer does not contain a forbidden phrase. It is 0 when the API wrote an answer.

Sufficiency is 1 when the outcome agrees with the label about whether an answer should be produced. `not_found` and `insufficient_evidence` both count as not producing an answer.

The report also records latency, model calls, prompt and completion tokens, estimated cost, the planned queries, the grade, and whether a retry added a chunk id. If the model omits token usage, the count is estimated at about 4 characters per token and the row says so.

Findings call out four situations:

- Agentic recall is higher than hybrid on the same question.
- Hybrid matches agentic recall and answer quality with lower latency or lower cost.
- An unanswerable question was answered.
- A retry did not add a chunk.

## API

```json
POST /api/evaluation/run
{ "source": "fixture", "modes": ["hybrid", "agentic"], "k": 5 }
```

`modes` defaults to both. `caseIds` can limit the run to ids from the dataset. `k` is 1–20 and defaults to `TOP_K`. The questions themselves are not taken from the request.

The response has `summary` (one row per mode and question type, plus an all-types row), `findings`, and `cases`. A question that throws is kept on `cases` with `error` set, and it is left out of the averages.

## Configuration

| Setting | Default | Role |
|---|---|---|
| `LLM_PROMPT_USD_PER_MILLION` | `0` | Price used for prompt tokens. `0` is the right value for a local model. |
| `LLM_COMPLETION_USD_PER_MILLION` | `0` | Price used for completion tokens. |

The V3 knobs still apply inside an agentic run: `AGENT_MAX_QUERIES`, `AGENT_MAX_RETRIES`, `TOP_K`, and the reranker settings. `AGENT_ENABLED` does not have to be true. The evaluation run calls the agent graph itself.

In code the scorer is `scoreCase` in `backend-server/src/evaluation/metrics.ts`. The runner is `runEvaluation` in `backend-server/src/evaluation/run.ts`.

## Limits

- The bundled questions are written for the fixture notes. They are a starting set, not a clinical benchmark.
- Fact coverage is a phrase check. A correct paraphrase that does not contain the labeled word scores low.
- The grade and the answer use the configured chat model. A weak local model can pass a bad grade or miss a fact that is in the passage.
- Hybrid sufficiency in production is only "were any passages returned." The extra grade on a hybrid row is recorded for the report.
- Token cost is zero until the two price settings are set. Estimated token counts are not the model's tokenizer.
- One run is sequential. Six questions on both modes is many model calls.
