# V6 — Observability

V6 records every chat question: how long retrieval and the answer took, how many model calls ran, and what those tokens cost. The search page shows that line under the answer. `/observe` lists the recent requests.

| Piece | What it records | Example |
|---|---|---|
| Request trace | One row per chat question | Path, outcome, latency, tokens, cost |
| Stage time | Retrieval, then the answer when one is written | Retrieve 420 ms, answer 1.8 s |
| Agent step time | How long each graph node took | Grade 310 ms |
| Tokens | Prompt and completion counts from the model | 840 prompt, 120 completion |
| Cost | Those tokens times the configured price | $0 for a local model |

```text
POST /api/chat
    ↓
Time the retrieval
Hybrid search, or plan → route → retrieve → grade → maybe rewrite or a tool
    ↓
Time the answer, when the outcome is answered
    ↓
Count model calls and tokens
    ↓
Store the trace and return it on the response
```

Evaluation in [v5.md](./v5.md) still scores a fixed question set on its own. Those runs do not go through `POST /api/chat`, so they do not appear in this log. PostgreSQL and the embedding server stay as they are.

## What a chat response adds

`POST /api/chat` now includes `observation`:

| Field | Meaning |
|---|---|
| `latencyMs` | Time from the start of the request to the response |
| `retrieveMs` | Time to search, including planning, grading, and retries when the agent is on |
| `generateMs` | Time to write the answer. Empty when the outcome is `not_found` or `insufficient_evidence` |
| `usage.calls` | Chat-model calls for this question |
| `usage.promptTokens` | Tokens read by those calls |
| `usage.completionTokens` | Tokens written by those calls |
| `usage.estimated` | True when a call did not report usage, so the count is about 4 characters per token |
| `usage.costUsd` | Prompt and completion tokens priced with the V5 rates |
| `path` | `agent` or `hybrid` |
| `citationCount` | Passages and tool results returned |

Each agent step also has `durationMs`. The search page prints it next to the step name.

A request that fails after the question is accepted is stored with outcome `error`, then the API still returns the error. A body that is not valid JSON is rejected before a trace is written.

## The log

`GET /api/observations` returns the newest traces and a summary of every trace still in memory: count, mean latency, token totals, cost, and counts by path and outcome. `limit` defaults to 50 and can be 1–200. The summary covers the whole log, not only that page.

The log lives in the API process. It keeps `OBSERVATION_LIMIT` rows (default 200) and drops the oldest. Restarting the API clears it. Set `OBSERVATION_ENABLED=false` to stop storing traces. The chat response still includes `observation` for the question that was just asked.

## Configuration

| Setting | Default | Role |
|---|---|---|
| `OBSERVATION_ENABLED` | `true` | Keep chat traces in memory |
| `OBSERVATION_LIMIT` | `200` | How many traces to keep. Allowed range 1–1000 |
| `LLM_PROMPT_USD_PER_MILLION` | `0` | Price for prompt tokens. `0` fits a local model |
| `LLM_COMPLETION_USD_PER_MILLION` | `0` | Price for completion tokens |

In code the record is `buildObservation` in `backend-server/src/services/observe.ts`. The chat route stores it after `withLlmUsage`. Step timing is `withDuration` in `backend-server/src/services/agent/graph.ts`.

## Limits

- The log is not written to PostgreSQL. A restart drops it.
- Token counts follow what the chat model reports. A missing usage field is estimated from text length.
- Cost stays $0 until the two price settings are set.
- `retrieveMs` includes every model call inside the agent, not only the database search.
- Evaluation runs are separate and do not show up here.
